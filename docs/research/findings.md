### 2.4 Кривая мощности

Бины 0.5 м/с, медиана p (T1): 0.03 @3.0, 0.15 @5.0, 0.40 @7.0, 0.71 @9.0, 0.93 @10.5, 0.98 @11.0, 0.99 с 11.5 до 21 м/с. IQR в крутой зоне 0.03–0.06. Макс. наклон 0.176/м/с при 7.9 м/с (0.11 при 6 и 10) → ошибка ветра 1 м/с ≈ 0.11–0.18 мощности. 47% часов (49–52% в Feb 2025 / Jan 2026) — в крутой зоне 5–11 м/с.

Логистическая аппроксимация:

| | Формула | R² / MAE (10-мин) | R² / MAE / RMSE (час) |
|---|---|---|---|
| T1 | p = 1/(1+exp(−0.705·(ws−7.89))) | 0.957 / 0.034 | 0.962 / 0.031 / 0.070 |
| T2 | a=0.700, b=7.98 | 0.970 / 0.030 | 0.973 / 0.029 / 0.058 |

Эмпирическая binned-median кривая: MAE 0.030 / 0.028. **Потолок при идеальном ветре — MAE ≈0.03**; вся ошибка прогноза придёт из NWP-ветра. Гондольный анемометр стоит за ротором и занижает свободный поток ([WES 2017](https://wes.copernicus.org/articles/2/295/2017/wes-2-295-2017.pdf)) — spec-кривую не использовать, NWP-ветер напрямую в SCADA-кривую не подставлять без калибровки.

```python
def power_curve(ws, a=0.705, b=7.89, cap=0.99, floor=0.01):
    return np.clip(1/(1+np.exp(-a*(np.asarray(ws,float)-b))), floor, cap)
```

### 3.2 Ловушки

1. **Historical Forecast и Archive best_match = lead 0–5 ч** (с 2025-10; ранее lead 1–12 / неизвестная склейка, §3.1). Это near-analysis; использовать для Feb 2026 = нарушить правило «архивный прогноз, а не поздний факт». Только для train.
2. **`models=best_match` в Archive возвращает IFS 9 км, не ERA5.** Реанализ — только явно `models=era5`. Иначе README опишет источник неверно.
3. **Ветер по умолчанию в km/h.** Всегда `wind_speed_unit=ms` (5.6 km/h → 1.55 m/s). Без параметра Single Runs даёт ws100 30.9 km/h вместо 8.57 m/s.
4. **`timezone=auto` / `Asia/Almaty` сдвигает окно.** Даёт GMT+5 (utc_offset 18000), времена локальные, значение Feb-1 00:00 меняется (7.6 vs 5.6); Single Runs также сдвигает метку прогона (t0 2026-01-31T05:00). Всегда `timezone=UTC`, а SCADA — фиксированный −6 ч.
5. **`best_match` в Previous Runs здесь сейчас резолвится в ecmwf_ifs 9 км** (архив 9 км в этом API — с 2025-10), при этом сам `best_match` отдаёт данные с 2024-03 → ряд неоднороден по подлежащей модели; для train-окна 2024–2026 брать явные модели.
6. Previous Runs: только целосуточные смещения (нет 6/12/36 ч) — точный прогноз «на момент выпуска» не восстановить; для этого Single Runs.
7. `timeformat=unixtime` даёт epoch (1769904000 = 2026-02-01T00:00Z) — удобно для join.
8. Модели сильно расходятся: 2026-02-01T00:00Z ws100 best_match 1.55, ECMWF 4.30, ICON 1.46, GFS 8.00 м/с; previous_day1: 1.49 / 0.63 / 1.77 / 10.78 → мультимодельный ансамбль обязателен.
9. **wind_gusts_10m null на lead 0** в каждом Single Run (gust — максимум за предыдущий час); DoD «0 null по всем переменным» упадёт — читать gusts с lead ≥1 или ffill.
10. **HTTP 200 ≠ данные**: 2025-08-09T06/12 отдают 200 со всеми null; полноту рана считать по `n_null` на переменную (manifest), не по статусу.
11. **id моделей**: AIFS = `ecmwf_aifs025_single` (`aifs` → 400 «Cannot initialize MultiDomains»; `ecmwf_aifs025` недоступен даже после 2026-04-02).
12. **Ответ Single Runs не несёт «available at»** — правило доступности рана (per-cycle AVAIL_LAG, §3.4) enforce'ится в коде и leak-тестом.
13. **ECMWF AWS: stream `scda` для 06/18Z deprecated с IFS Cycle 50r1** — в бакете `scda` до 2026-05-11, `oper` с 2026-05-12; для Feb 2026 replay `scda` верен, в live-режиме stream по часу цикла не хардкодить. `_length` поля в `.index` разный у каждого рана — всегда читать из индекса.
14. **`previous_dayN` для ifs025/AIFS — интерполяция между ранами** на не-нативных часах (§3.1): «per-hour provenance» как фича заявлять только для ecmwf_ifs / icon_global / gfs_global.

### 3.4 ECMWF AWS GRIB — путь

Layout: `{YYYYMMDD}/{HH}z/ifs/0p25/{stream}/{YYYYMMDD}{HH}0000-{step}h-{stream}-fc.grib2` + `.index`. 00Z/12Z → stream `oper` (0–144 ч каждые 3 ч, далее 6-часово до 360), 06Z/18Z → `scda` (0–144 ч, 3-часово) **до 2026-05-11**, с 2026-05-12 (IFS Cycle 50r1) — `oper`, `scda` deprecated (для Feb 2026 replay `scda` верен; в live-режиме stream по часу цикла не хардкодить); `enfo` — ансамбль. В бакете только `ifs/0p25` — 9 км продукта нет (на 2026-09-22). Surface-параметры в 24-ч файле: 100u, 100v, 10u, 10v, 10fg, 2t, 2d, sp, msl, skt. Файл шага ~128 МБ, но `.index` (JSON-строки с `_offset`/`_length`) даёт byte-range: 100u на 24 ч = 1,405,605 байт для рана 2026-02-01 00z (у других ранов длина другая: 1,404,261 у 12z, 1,290,080 у 2026-09-01 — всегда читать из `.index`); cfgrib → u100 в ближайшем гриде (43.75, 78.5) = −10.52 м/с, valid 2026-02-02T00:00. Клиенты: [ecmwf-opendata](https://github.com/ecmwf/ecmwf-opendata) (`Client(source='aws')`), [Herbie](https://herbie.readthedocs.io/en/latest/gallery/ecmwf_models/ecmwf.html) (`Herbie('2026-02-01', model='ifs', product='oper', fxx=24)`; aws с 2023-01-18, azure с 2022-01-21, ecmwf.int только 4 дня). Выполнено end-to-end в ресёрче (GRIB-хелпер `ecmwf_aws_field` в репо не переносился; в репо только Open-Meteo клиент `research/openmeteo_client.py`). Кросс-проверка provenance: AWS ран 2026-02-01 00z step 24 билинейно к турбине = 6.78 м/с / 72° vs Open-Meteo single run lead 24 = 6.84 м/с / 65° — тот же as-issued ран. Ограничения пути: 3-часовой шаг (линейная интерполяция до часа даёт MAE 0.32 м/с, max 1.9, vs почасовой 9 км ряд на lead 24–48), обе турбины в одной 0.25° ячейке, полный Feb-replay ≈15k S3-запросов при `SlowDown` (242 из 300 параллельных → 503; последовательно 1–4 req/s проходит) → GRIB-путь только вторичный/provenance, primary — Single Runs 9 км.

**Тайминг публикации (исправлено верификацией; было «≈06:30/18:30, константа +7 ч»).** ECMWF real-time dissemination ([schedule](https://confluence.ecmwf.int/display/DAC/Dissemination+schedule)): шаги 0–90 ч 00z 05:45→06:12, 06z 11:45→12:12, 12z 17:45→18:12, 18z 23:45→00:12 UTC; до 144 ч — +6:27; 150–360 ч (только 00z/12z) — до 07:34/19:34. **Free open data (data.ecmwf.int / AWS `ecmwf-forecasts`, 0.25°) публикуется в конце всего расписания**: Last-Modified для всех ранов 31.01–28.02.2026 (и сентября 2026) — **00Z 07:34, 06Z 12:27, 12Z 19:34, 18Z 00:27 UTC** (+7.57 ч / +6.45 ч; README ecmwf-opendata: «between 7 and 9 hours»). 9 км HRES в бесплатном open-data subset в Feb 2026 не было (только 25 км; 9 км обещан «later in 2026» с 2-ч задержкой); Open-Meteo `ecmwf_ifs` 9 км идёт с real-time dissemination «без дополнительной задержки» и становится доступен ≈07:00–07:15 (00Z), 12:20–12:30 (06Z), 19:00–19:15 (12Z), 00:15–00:25 (18Z) UTC (`meta.json` `last_run_availability_time` = init+7.0 ч; ecmwf_ifs025 +7.8 ч, AIFS +5.7 ч, icon +3.75 ч, gfs +6.5 ч; ретроспективно за Feb 2026 не проверить — per-run архив Open-Meteo только с 2026-06).

**Следствие: константа `init + 7 ч` НЕ leak-safe для 00Z/12Z** — пускает 12Z в 19:00 UTC, когда он публичен только с 19:34 (open data) / ~19:15 (Open-Meteo 9 км), и 00Z в 07:00 vs 07:34. Правило — per-cycle, целочисленные лаги: **`AVAIL_LAG['ecmwf_ifs'] = {00Z: 8h, 06Z: 7h, 12Z: 8h, 18Z: 7h}`** → раны допускаются с **08:00 / 13:00 / 20:00 / 01:00 UTC** (публикация open data 07:34/12:27/19:34/00:27 UTC → запас 26–33 мин; альтернатива — явные времена 07:35/12:30/19:35/00:30, не используем, чтобы README, триггеры и `clock.py` считали одно и то же; источники — Last-Modified бакета `ecmwf-forecasts` и `api.open-meteo.com/data/ecmwf_ifs/static/meta.json`). Под ним: выпуск 18:00 UTC D−1 (= 00:00 SCADA дня D) → ран **06Z D−1, lead 12–59 ч** на окно 18:00 UTC D−1 … 17:00 UTC D+1 — официальный day-ahead; **re-issue на 12Z — только с 20:00 UTC** (02:00 SCADA дня D), 18Z — с 01:00 UTC D, 00Z — с 08:00 UTC D; выпуск 03:00 UTC D−1 (дедлайн рынка 08:00 Астаны) → ран 18Z D−2, lead 24–71 ч (нужен `forecast_days=4`; покрывает +15…+62 ч от выпуска). Leak-тест обязан падать на issue 19:00 UTC с 12Z-раном. Таблица «ран → канал → время публикации → лаг» ниже (дублируется в README). Прежняя формулировка «прогноз, выпущенный 31 января = прогон 31-Jan 12Z (≈18:30 UTC)» снята: 12Z публичен в 19:34 UTC = 01:34 SCADA 1 февраля, т.е. уже внутри целевых суток — годится только как intraday re-issue; семантику выпусков (dayahead vs reissue) фиксировать явно (§7 п.4). ### 4.2 Рекомендуемый стек (по трудозатратам)

1. Канонический почасовой датасет (UTC, ≥4 из 6 сэмплов, флаги).
2. Бейзлайны: persistence, климатология, Madsen «new reference» a_k·P(t)+(1−a_k)·mean, NWP → binned SCADA-кривая после линейного MOS ws_NWP → ws_nacelle с плотностной нормировкой.
3. **Основная модель: LightGBM `objective='quantile'`, alpha ∈ {0.1, 0.5, 0.9}** (или CatBoost MultiQuantile), pooled по T1+T2 с `turbine_id`. **Train/serve consistency (исправлено по критике):** в инференсе модель получает Single Runs 06Z с lead 12–59, значит и учить на тех же лидах — **дамп Single Runs ecmwf_ifs 2024-03-14 → 2026-01-31** (1 ран/день по правилу Clock: 06Z; для 2024-03-14…2024-08-09 (06Z непрерывно с 2024-08-10) — 00Z с lead 18–65; fallback выбирать по факту 400 / all-null (manifest), не по дате; `forecast_days=4`, 7 переменных; ~690 вызовов через кеш; полнота по null, не по HTTP 200), признаки `lead_h` (числовой, train покрывает 12–59) и `run_cycle`; Previous Runs других моделей — вторичные признаки **с той же маской доступности в train и test** (архив ecmwf_ifs в Previous Runs только с 2025-10-01 — как primary он съедал бы треть holdout Jan 2026 и давал другие лиды 24–53). Train 2024-03 → 2025-12 без Feb 2025, validate Feb 2025 + Jan 2026 as-of тем же кодом. Clip [0,1], сортировка квантилей (нет crossing). Оговорка в README: до 2025-10 архив Single Runs 9 км — hindcast Cycle 49R1 (по докам Open-Meteo), Feb 2026 — real-time.
4. Если успеваем: SVK-стекинг (CatBoost per NWP + линейная QR-мета) или просто среднее квантилей по NWP; MAPIE EnbPI (`TimeSeriesRegressor(method='enbpi', cv=BlockBootstrap)`) при плохой калибровке.
5. Опционально для «оригинальности»: nixtla neuralforecast NHITS с `futr_exog_list` = NWP ([docs](https://nixtlaverse.nixtla.io/neuralforecast/docs/capabilities/exogenous_variables.html)); TFT/N-BEATS/LSTM как primary — нет.

Библиотеки: pandas/numpy, lightgbm, catboost, scikit-learn, shap, mapie (опц.), windpowerlib (density/height, опц.), openoa — скопировать 3–4 фильтра вместо тяжёлой зависимости, openmeteo-requests + requests-cache + retry-requests, matplotlib/plotly.

### 4.3 Признаки

| Группа | Признаки |
|---|---|
| NWP ветер | ws 10/80/100/120 м по каждой модели (ecmwf_ifs — Single Runs, lead 12–59; icon_global, ecmwf_aifs025_single, ecmwf_ifs025, gfs_global — Previous Runs day1/day2 с маской доступности; ws80/120 у ifs025/AIFS null); ws100³; среднее и spread по моделям; лаги/разности ws100 ±1, ±2 ч |

```python
rho = (p_hpa*100.0) / (R_D*(t_c+273.15)); v_n = ws*(rho/1.225)**(1/3)
```

### 4.4 Очистка (флаги, не удаление; train на чистых, eval на всех)

| Правило | Порог |
|---|---|
| range | ws ∉ [0,30] или p ∉ [0,1] |
| frozen | Δp==0 & Δp(2)==0 & Δws==0; конкретно — 2025-05-14 12:10–15:30 |
| downtime | ws > cut-in+1 & p≤0.005; в EDA-варианте p≤0.01 & ws>5 |

### 4.5 Протокол оценки

- Rolling-origin backtest, зеркалящий тест: ежедневный выпуск, горизонты h=1..48, только прогоны с `init + AVAIL_LAG[cycle] ≤ issue_time` (§3.4). Holdouts: **Feb 2025, Jan 2026** (as-of NWP-бэктест); **Feb 2024** (ветреный, p 0.454) — только наивные бейзлайны и потолки (ERA5 / SCADA-кривая): lead-aligned архивных прогнозов за этот месяц нет (Previous Runs icon/gfs полные с 2024-03-01, ifs025 с 2024-04-01; Single Runs ecmwf_ifs с 2024-03-14; Historical Forecast 2024-03→11 не совпадает ни с одним lead). As-of прогон тем же кодом на окнах `dev` (Jan 2026) и `feb2025` (репетиция того же сезона, Single Runs ecmwf_ifs по Clock) и `market` (`ISSUE_HOUR_UTC=3`). Feb 2026 не трогать; для него — псевдо-оценка на уровне ветра: as-of ws100 (lead 12–59) vs Historical Forecast (lead 0–5) и ERA5, только в `evaluate_*`.
- Метрики по Madsen: nBIAS(k), nMAE(k), nRMSE(k), SDE(k) на каждый lead и по блокам h1–24 / h25–48; skill = 100·(MAE_pers − MAE_model)/MAE_pers и skill vs case-compliant бейзлайна NWP→кривая (цель ≥10%, §2.5); pinball loss и покрытие P10–P90; reliability diagram; error-vs-lead; пример недели.
- Считать только часы с данными SCADA (n≥4); отдельно — без outage-часов (остаток < −0.3), чтобы показать weather-explainable skill vs raw.
- Таблица бейзлайнов рядом (§2.5). Точечный прогноз — медиана для MAE, среднее для RMSE: уточнить у организаторов.
- Объяснимость: feature importance + SHAP, scatter raw vs clean кривой, NWP-vs-nacelle bias plot.

Не для ядра: Claude Agent SDK (subprocess, bash/fs surface), CrewAI, OpenAI Agents SDK (через LiteLLM), smolagents (не подтверждено).

**Что код / что LLM:**

| Код (детерминированно) | LLM (планировщик) |
|---|---|

Каждое решение — в `trace.jsonl` |

**Tools:** `get_clock`, `fetch_nwp_forecast` (Single Runs ecmwf_ifs, последний прогон с `init + AVAIL_LAG[cycle] ≤ issue`, §3.4), `fetch_nwp_ensemble` (Previous Runs day1/day2, 3+ модели, с маской доступности), `fetch_scada_history` (строки ≤ issue time), `check_data_quality`, `prepare_features` (одна схема train/infer), `predict_power` (LightGBM quantiles, T1/T2), `compare_with_previous`, `evaluate_forecast`, `detect_drift` (none | bias_correct | retrain), `apply_bias_correction` (rolling_bias_7d), `save_forecast` (SQLite + `runs/<issue>/forecast.csv`), `read_memory`/`write_memory`, `write_report`. `UsageLimits(request_limit=25)`.

**As-of clock / anti-leakage (исправлено верификацией):** лаги per-model по каналу, который реально используется (Open-Meteo, `meta.json` `last_run_availability_time`, округление вверх до целого часа): `AVAIL_LAG = {'ecmwf_ifs': {0: 8h, 6: 7h, 12: 8h, 18: 7h}, 'ecmwf_ifs025': 8h, 'ecmwf_aifs025_single': 6h, 'icon_global': 4h, 'gfs_global': 7h}` (ecmwf_ifs: open data публична 07:34/12:27/19:34/00:27 UTC; ecmwf_ifs025 в Open-Meteo — init+7.8 ч, измерено 2026-09-22: 00Z 07:41, 06Z 13:09, 12Z 19:40, 18Z 01:04 UTC → лаг +7 ч пускал бы 06Z/18Z в 13:00/01:00, на 4–9 мин раньше публикации, поэтому 8 ч на все циклы; +8/+7 для ifs025 верны только для AWS `ecmwf-forecasts` (12:27/00:27); AIFS +5.7 ч, ICON +3.75 ч, GFS +6.5 ч; таблица — §3.4), `allowed_runs = [r for r in runs if r.init + AVAIL_LAG[r.model][r.cycle] <= issue_time]`, та же формула на каждое значение `previous_dayN` (§3.1; недоступный ран → NaN); константа +7 ч пускала 12Z в 19:00 UTC — утечка. Unit-тест `test_clock_no_leakage.py` обязан падать на issue 19:00 UTC с 12Z-раном и на импорте Historical Forecast / Archive (analysis-источники) в `predict_*`/`prepare_features`; ни одно значение — из прогона после issue time.

**Триггеры (event queue):** SCHEDULED_ISSUE — официальный dayahead 18:00 UTC D−1 (00:00 SCADA дня D, ран 06Z D−1, lead 12–59; market-режим `ISSUE_HOUR_UTC=3` → 18Z D−2, lead 24–71); NWP_RUN по факту доступности рана (`init + AVAIL_LAG`): 12Z в 20:00, 18Z в 01:00, 00Z в 08:00, 06Z в 13:00 UTC (re-issue обновляет только `target_time > issue_time`; `issue_kind ∈ {dayahead, reissue}` во всех CSV, `SUBMISSION_ISSUE_KIND=dayahead`); SCADA_BATCH ежечасно (только dev-окно); RESIDUAL_ALERT при |z| остатков за 6 ч > 2.5; DIVERGENCE_ALERT при расхождении 24-ч среднего ветра нового прогона с последним выпущенным > 1.5 м/с. Агент решает, менять ли опубликованный прогноз.

**Окна одним кодом:** `--window dev` (Jan 2026, факты есть → evaluate/drift/residual демонстрируются), `--window feb2025` (репетиция того же сезона тем же as-of кодом, MAE рядом с Jan 2026 в README) и `--window test` (2026-01-31..02-28, факты скрыты → триггеры NWP_RUN + divergence; пишет `submission/forecast_feb2026_dayahead.csv` / `_intraday.csv`: issue_time, target_time (SCADA + UTC), turbine, lead_h, nwp_run_init_utc, issue_kind, p10, p50, p90 (в research.json — power_p50; унифицировано с SQLite-схемой) плюс плоский `forecast_feb2026_hourly.csv` — одна строка на час × турбина, 672 × 2, с `plant_mw`/`energy_mwh`).

**Без ключа:** `LLM_MODE=scripted` — ScriptedPlanner с тем же интерфейсом, теми же tool-вызовами и форматом трейса; `make verify` в scripted-режиме < 2 мин.
