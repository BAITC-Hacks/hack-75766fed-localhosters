# Биржану: подключение первой ML-модели к проекту

## 1. Что подключаем первым

**Первая рабочая модель — CatBoostRegressor, отдельно обученный для каждой из двух турбин.** Получи от Акылбека две модели `.cbm` и Python-пакет с функцией `predict_power`. Подключи этот пакет к бэкенду, затем покажи его ответы в веб-интерфейсе.

Модель принимает прогноз погоды на следующие 24 или 48 часов и возвращает среднюю нормализованную мощность за каждый час. Один вызов относится к одной турбине. Полный прогноз на 48 часов для двух турбин — два вызова по 48 значений.

CatBoost — алгоритм, а не готовые предобученные веса этих турбин. Одной установки библиотеки недостаточно: артефакты обучает и передаёт Акылбек. Рамазан предоставляет погодные данные. Твоя задача — соединить компоненты и сделать рабочий пользовательский сценарий; план обучения находится в [инструкции для ML](02_ML_IMPROVEMENT.md).

**Критерий первого результата:** выбрать дату и турбину → получить допустимый погодный прогноз → вызвать модель → сохранить результат → показать график.

Это инструкция по реализации. Перечисленные ниже модели, функции, API и примеры ещё нужно создать; документы не означают, что обученные веса уже лежат в репозитории.

## 2. Какой пакет получить от ML-участника

Предлагаемая структура поставки; перечисленные файлы нужно создать при реализации:

```text
ml/
  README.md                     # установка, вызов, запуск примера
  requirements.txt              # проверенные фиксированные версии
  inference.py                  # загрузка артефактов и predict_power
  features.py                   # общая подготовка признаков
  schema.json                   # запрос, ответ, ошибки
  examples/
    request_48h.json
    expected_response.json
  artifacts/
    turbine_1.cbm
    turbine_2.cbm
    metadata.json
  reports/
    validation.json
```

Метаданные содержат версии модели и схемы, список признаков в нужном порядке, источник погоды, временные соглашения, последний использованный целевой интервал, время доступности последних обучающих данных, фактическую дату сборки артефакта, параметры и метрики.

Дата сегодняшней сборки артефакта и исторический срез данных — разные вещи: для воспроизведения прошлого проверяем именно доступность всех обучающих входов и ответов на тот момент.

Критерии готовности первой поставки:

- [ ] Боржан запускает пример в чистом окружении по README.
- [ ] Обе турбины возвращают 48 конечных значений в диапазоне 0–1.
- [ ] Ошибочный вход выдаёт понятную ошибку.
- [ ] Прогноз настоящей модели показан на графике с правильными часовыми интервалами.
- [ ] Версия модели и режим demo/model различимы.
- [ ] Есть сравнение с простым ориентиром на отложенном периоде.
- [ ] Для инференса не нужны обучающие CSV и доступ к исследовательскому ноутбуку.

## 3. Формат запроса и ответа

Предлагаемый интерфейс Python-пакета:

```python
predict_power(request: dict) -> dict
```

Модели загружаются один раз при старте процесса. Боржан оборачивает функцию в HTTP-метод, например `POST /api/v1/power-forecast`. ML-участнику не требуется поднимать отдельный сервис для первого подключения.

Один запрос относится к одной турбине. Для двух турбин бэкенд делает два вызова. В продукте используются горизонты 24 и 48; для небольших интеграционных примеров функция может принимать любой целый горизонт от 1 до 48.

Ниже полный пример на два часа с вымышленной погодой. Указанное время доступности служит иллюстрацией структуры, а не расписанием реального провайдера.

```json
{
  "schema_version": "1.0",
  "turbine_id": "turbine_1",
  "forecast_origin_utc": "2026-02-05T00:00:00Z",
  "horizon_hours": 2,
  "weather_source": "example-provider",
  "weather_model": "example-model",
  "weather_run_time_utc": "2026-02-04T18:00:00Z",
  "weather_available_at_utc": "2026-02-04T23:00:00Z",
  "hourly": [
    {
      "valid_time_utc": "2026-02-05T01:00:00Z",
      "wind_speed_100m_ms": 8.4,
      "wind_direction_100m_deg": 237.0,
      "temperature_2m_c": -2.4
    },
    {
      "valid_time_utc": "2026-02-05T02:00:00Z",
      "wind_speed_100m_ms": 8.1,
      "wind_direction_100m_deg": 240.0,
      "temperature_2m_c": -2.6
    }
  ]
}
```

Пример ответа демонстрационной реализации; числа синтетические:

```json
{
  "schema_version": "1.0",
  "model_version": "demo-v0",
  "prediction_kind": "demo",
  "turbine_id": "turbine_1",
  "forecast_origin_utc": "2026-02-05T00:00:00Z",
  "horizon_hours": 2,
  "target": "hourly_mean_normalized_active_power",
  "interval_label": "end",
  "hourly": [
    {
      "valid_time_utc": "2026-02-05T01:00:00Z",
      "power_normalized": 0.61
    },
    {
      "valid_time_utc": "2026-02-05T02:00:00Z",
      "power_normalized": 0.57
    }
  ]
}
```

Обученная модель возвращает ту же структуру, но `prediction_kind = "model"` и свою реальную версию, например `catboost-v1`. UI не должен выводить «точность 92%» из MAE или придумывать доверительный интервал. Метрики берутся из отдельного отчёта с указанным периодом проверки.

### Проверки на входе

- Известные версия схемы и идентификатор турбины.
- Совместимый с моделью погодный источник и набор полей.
- UTC-время; запуск на границе часа; погодный выпуск доступен к моменту расчёта.
- Ровно `horizon_hours` строк, без дублей и пропусков, с последовательными метками +1…+H.
- Правильные единицы, конечные числовые значения, неотрицательная скорость ветра.
- Для обученной модели — обучение завершено на данных, доступных не позже данного исторического момента расчёта.

В v1 при отсутствии обязательной погоды возвращаем понятную структурированную ошибку, например `INVALID_INPUT`, `WEATHER_NOT_AVAILABLE`, `INCOMPLETE_HORIZON`, `MODEL_NOT_FOUND` или `MODEL_NOT_ELIGIBLE_AT_ORIGIN`. Не подставляем нулевой ветер или демонстрационный прогноз автоматически. Политику повторного запроса реализует агент.

## 4. Порядок подключения

1. **Согласовать схему с Акылбеком и Рамазаном.** Зафиксировать поля, уровень ветра, единицы, часовые интервалы и погодный источник. Вариант с ветром на 100 м в примере нужно подтвердить по архиву; это не известная высота турбин. Не передавать ветер на 10 м под названием 100 м.
2. **Запустить поставляемый пример локально.** Установить зависимости из ML-пакета, загрузить две модели и получить ответ через `predict_power`. Для инференса обучение заново не требуется.
3. **Подключить к бэкенду.** Если бэкенд на Python, импортировать функцию прямо в приложение. Если на другом языке, обернуть тот же пакет небольшим Python HTTP-сервисом. Подготовка признаков в обоих случаях остаётся внутри ML-пакета.
4. **Подключить погодный адаптер.** Передавать данные Рамазана в согласованном формате. Для исторического запуска выбирать прогноз, опубликованный не позже момента расчёта. Не брать фактическую погоду будущего часа.
5. **Сохранять вход и результат.** Хранить турбину, момент расчёта, погодный выпуск, входную погоду или ссылку на сохранённую копию, версию модели и все почасовые прогнозы.
6. **Подключить интерфейс.** Выбор даты, турбины и горизонта; график мощности; версия модели; состояние загрузки и понятное сообщение при ошибке. Показывать турбины отдельно.
7. **Проверить полный сценарий.** По одной исторической дате получить прогноз обеих турбин. После этого подключить последовательный ежедневный запуск февраля и пересчёт при обновлении входных данных.

Модели загружать один раз при старте процесса, не при каждом HTTP-запросе. Агент управляет получением погоды, проверкой, вызовом модели и повторными попытками; числовой прогноз рассчитывает ML-пакет.

### Что показывать в интерфейсе

- Ось Y: «Нормализованная мощность, 0–1». Это не МВт и не МВт·ч.
- Ось X: часовой интервал. Метка `01:00` означает среднее за `[00:00, 01:00)` при согласованной маркировке концом часа.
- Результат на 48 часов покрывает следующие 48 последовательных интервалов, а не только часы +24…+48.
- Время хранится и передаётся в UTC; при показе в местном времени часовой пояс подписывается явно.
- Факт для сравнения показывать только там, где он действительно есть. В предоставленных файлах нет фактической мощности февраля 2026 года.
- Не складывать две нормализованные мощности в «общую выработку ВЭС», пока не определены номиналы и правила нормализации.

## 5. Как начать до готовности весов

Вначале получи от Акылбека примеры запросов и ответов и подключи отдельную демонстрационную реализацию той же функции. Она возвращает синтетические данные с `prediction_kind = "demo"`; UI явно подписывает их как демонстрационные.

После получения первой обученной CatBoost-модели заменяешь реализацию и артефакты, сохраняя формат API. Для настоящей модели возвращаются `prediction_kind = "model"` и её версия.

Демонстрационная реализация помогает собирать UI и бэкенд, но не является тестом точности ML. При ошибке настоящей модели нельзя молча переключаться на demo или подставлять нулевую погоду.

## 6. Как подключать улучшенные версии

Разделяем `schema_version` и `model_version`.

- Новое обучение с теми же входами меняет только `model_version`.
- Новые признаки, вычисляемые внутри пакета из старых входов, не требуют изменения бэкенда.
- Новые обязательные погодные поля требуют согласования с Рамазаном и новой версии схемы либо совместимого адаптера. Молча делать старые запросы недействительными нельзя.
- Боржан загружает новую проверенную поставку, запускает интеграционные примеры и сохраняет возможность вернуться к предыдущей.
- Каждый прогноз хранится вместе с версией модели, входной погодой или её идентификатором, временем запуска и погодным выпуском.
- Старые результаты не перезаписываются без сохранения версии: иначе сравнение экспериментов станет невоспроизводимым.

## 7. Когда первый этап завершён

- [ ] Приложение вызывает настоящую CatBoost-модель для обеих турбин.
- [ ] Погода приходит из адаптера Рамазана с проверкой времени доступности.
- [ ] На графике есть 24 или 48 последовательных часовых значений на турбину.
- [ ] Неверный запрос или неполная погода приводят к понятной ошибке.
- [ ] Результат можно воспроизвести по сохранённому входу и версии модели.
- [ ] Новая поставка модели подключается без изменения UI при неизменной схеме.

После этого Акылбек улучшает качество по [ML-плану](02_ML_IMPROVEMENT.md), а ты продолжаешь работу над агентом, бэкендом и интерфейсом.
